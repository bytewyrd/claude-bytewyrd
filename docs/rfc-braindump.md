# RFC Braindump

Potential RFC ideas. Add with `/rfc-braindump`, promote to full RFC with `/rfc-new`.

* **Enforce evidence-based research for rfc-architect.** Update the `rfc-architect` agent's instructions to require verification of all external facts (APIs, library behavior, tool capabilities, version-specific details) via Context7 or Exa before including them in an RFC — training knowledge alone is not an acceptable source. This addresses the risk of RFCs being drafted with outdated or hallucinated technical details that later derail implementation. Approach hints: mirror the "Evidence-Based Development" guidance already in `CLAUDE.md`, and consider adding a self-check step to the RFC self-review checklist that flags unverified claims.
* **`/rfc-summary` command for active RFC overview.** Add a new skill/command that lists all RFCs currently in `Draft` or `Approved` status, filtering out `Done` and `Dropped` entries to surface only work that is pending design feedback or awaiting implementation. This solves the discoverability problem of scanning `docs/rfcs/` manually to figure out what's in-flight, especially as the parking lot grows. Output should be concise (e.g., status, title, identifier) so it works as a quick standup-style snapshot rather than a full report.
* **Post-Approval Discretionary Revisions section in RFC template.** Add a dedicated section to the RFC template where implementers can log small clarifications, typo fixes, or non-breaking adjustments made after an RFC reaches Approved status, without requiring a full re-approval cycle. This solves the current ambiguity around minor in-flight changes during implementation — today there's no clear place to record them, so they either bloat commit messages, get lost, or trigger unnecessary re-review. Constraints: revisions must be non-breaking and not alter the core design decisions; anything substantive should still go back through review. The section should make it easy to audit what changed between Approved and Done states.
* **`/sync` enforces GitHub branch auto-delete setting.** Extend `/sync` to inspect a project's GitHub repository settings (when the project is hosted on GitHub) and ensure that "automatically delete head branches after merge" is enabled, bringing remote configuration under the same idempotent convention-enforcement umbrella that currently only covers local repo state. This solves the recurring problem of stale merged branches accumulating on the remote because the setting was never flipped on at repo creation. Key constraints: detect GitHub remotes reliably, use the GitHub MCP (or `gh` CLI fallback) with appropriate auth scopes, skip cleanly on non-GitHub remotes or when permissions are insufficient, and surface the change to the user rather than silently mutating remote settings.
* **Drop dates from BEST_PRACTICES entries.** Remove date stamps from all entries in `~/.claude/BEST_PRACTICES.md` and `docs/BEST_PRACTICES.md`, and update the `best-practices-record` and `best-practices-extract` skills to stop emitting them. Dates add noise without signal: a practice's value is its content, not when it was first captured, and stale dates make entries feel outdated even when the lesson is still correct. Scope covers stripping dates from existing entries, updating the writer skills, and confirming `best-practices-sync` (which promotes entries into plugin sync content) does not rely on dates for ordering or deduplication.
* **User-scope installation with requirement-check hooks.** Allow the bytewyrd plugin to be installed at user scope (applying globally across all projects) rather than requiring per-project installation. Add session-start or pre-task hooks that verify the active project meets the plugin's runtime requirements — companion plugins installed, required MCP servers configured, expected tooling present — and surface clear warnings or errors when prerequisites are missing. This removes the friction of per-project setup while preserving correctness: instead of enforcing requirements through installation scope, enforce them at the moment they actually matter. Open questions: which checks are warnings vs. hard failures, how to make the diagnostics actionable (e.g., point to the exact fix), and whether some skills should silently no-op on unsupported projects rather than warn.
* **Unify destination of `/best-practices-record` and `/best-practices-extract`.** Today `/best-practices-record` writes manually-captured entries to the global `~/.claude/BEST_PRACTICES.md`, while `/best-practices-extract` writes session-distilled entries to the project-local `docs/BEST_PRACTICES.md` — an inconsistency that splits the same conceptual data across two destinations with no clear rationale. The RFC should pick an intentional model: either both skills target the same file, or each writes to a clearly-justified scope with an explicit promotion path between local and global (e.g. extract-to-local then curate-to-global via `/best-practices-sync`). Key questions to resolve: what belongs project-local vs. cross-project, how does an entry get promoted, and does `/best-practices-extract` need a global-write variant for stack-level lessons surfaced mid-session.
