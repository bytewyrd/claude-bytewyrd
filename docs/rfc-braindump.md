# RFC Braindump

Potential RFC ideas. Add with `/rfc-braindump`, promote to full RFC with `/rfc-new`.

* **Modular Plugin Feature Toggles.** Restructure the plugin so it ships as a set of opt-in features (e.g., RFC workflow, refactor skill, best-practices extraction) that consumers can enable or disable during `/sync` setup, with a small set of core features that are always installed. This solves the current all-or-nothing adoption problem — some projects don't want or need the RFC process, but today installing the plugin means inheriting everything. Key design questions to resolve later: which features qualify as core vs. optional, how the toggle state is stored and re-applied on `/sync` re-runs, and how features declare their boundaries so they can be cleanly excluded without breaking cross-feature references.
* **Auto-prompt PR creation in /rfc-new and parallelize /rfc-new-braindumps.** Extend `/rfc-new` so that whenever GitHub is available (gh CLI authenticated or the GitHub MCP responding), it always asks the user whether to open a PR for the freshly drafted RFC, removing the current manual step of pushing and opening one by hand. Additionally, refactor `/rfc-new-braindumps` to fan out a parallel workflow that invokes `/rfc-new` once per braindump entry concurrently, rather than processing them sequentially, so converting an accumulated batch of ideas into Draft RFCs scales with the number of items instead of with total runtime.
* **Auto-rehydrate context after compaction.** Build a mechanism that, immediately after a compaction event, automatically reloads a curated set of high-value files back into context so the agent doesn't lose critical working memory. Selection must be deliberately conservative — pulling everything defeats the point of compaction — and should prioritize files actively being edited, the current plan/RFC, and project conventions over speculative dependencies. Open questions: how to detect "important" (recency, edit count, explicit pinning, plan references?), where the policy lives (settings, hook, skill), and how to avoid re-bloating context with stale or tangential files.
* **Tight worktrunk integration for worktree workflows.** Replace the plugin's manual `git worktree add` conventions with first-class integration of the `worktrunk` CLI, so session-start checks, new-branch creation, and worktree cleanup all flow through worktrunk's commands and hooks rather than ad-hoc git plumbing. This consolidates worktree management into a single well-tested tool, lets the plugin lean on worktrunk's project hooks (`.config/wt.toml`) for commit-message generation and automation, and removes drift between the plugin's documented workflow and what users actually run. Key constraints: worktrunk must be available on the user's PATH (graceful fallback or clear setup guidance when missing), and existing skills (`/sync`, RFC implement, branch cleanup) need to be updated to invoke worktrunk consistently instead of raw git commands.
* **Enforce branch+PR discipline in /rfc-new.** Update the `/rfc-new` skill so that creating any RFC — including promoting braindump entries — always creates a dedicated `rfc/<slug>` branch and opens a PR, never committing directly to main. This addresses a real failure where three Draft RFCs (#7, #13, #25) landed on main via bulk commit 346fe6a, bypassing review entirely. Branch creation and PR opening must be non-optional steps in the skill flow, and bulk braindump promotion should parallelize the branch+PR workflow per-RFC rather than batching multiple RFCs into a single commit.
* **Standardize on merge commits and enforce at the repo layer.** Update agent instructions and project conventions (`CLAUDE.md`, commit/PR skills, relevant agent definitions) to require merge commits — not rebase or squash — when merging PRs and pulling `main` into feature branches, so `/commit-push-pr`, RFC implementation, and ad-hoc merges behave consistently. Rebase remains acceptable in narrow cases, but the default avoids rewriting shared history, protects existing checkouts from forced updates, and preserves an auditable record of conflict resolution. Complement this with a `/github-verify` check that inspects each repository's GitHub merge strategy settings and flags any repo permitting squash or rebase merges — belt-and-suspenders enforcement so a contributor can't bypass the policy by clicking the wrong button.
* **Replace numbered braindump prompt in `/rfc-new` with `AskUserQuestion`.** When `/rfc-new` is invoked without an argument, it currently lists braindump entries as a numbered text list and asks the user to type a number — error-prone and slower than clicking. Swap that flow for the `AskUserQuestion` tool so each braindump entry surfaces as a real clickable option in the Claude Code UI, with the entry title as the option label and the full entry text as the description. Key constraint: only the no-argument path changes — explicit-argument invocations keep their current behavior. Approach hint: map braindump entries to AskUserQuestion options at the point where the numbered prompt is built, preserving the existing "create new RFC from scratch" escape hatch as one of the selectable options.
* **Summarize RFCs in `/rfc-new` final output.** Today the skill ends by printing the RFC file path and a changelog of auto-fixed bugs, forcing the human to open the file to know what was actually proposed. Extend the final presentation to include a high-level summary of the drafted RFC — problem, proposed change, key constraints, and notable design decisions — so the reviewer can sanity-check the direction inline before deciding whether to read the full file. Keep the summary tight (a few sentences or short bulleted sections) and derive it from the RFC content the architect just wrote, not a re-analysis. Preserve the existing path and auto-fix changelog beneath the summary.
* **Move plugin state to `.bytewyrd/` and commit version tracking.** Today bytewyrd writes bootstrap manifest, installed-version, and last-sync state into `.claude/` — Claude Code's own namespace — and gitignores it, so teams have no visible audit trail of plugin state. Carve out a dedicated `.bytewyrd/` directory for all plugin-generated tracking files and commit them like a lockfile, so the installed version and last `/sync` timestamp are reviewable in PRs and consistent across the team. Only ephemeral runtime sentinels (e.g. `precompact-extraction-done`) stay gitignored. Constraints: `enabledPlugins` and hook registrations must remain in `.claude/settings.json` because Claude Code reads them there; `/sync` needs to be rewritten to target `.bytewyrd/`; and existing consumer projects need a one-shot migration step that moves state out of `.claude/` without losing history.
* **Include braindumps in /rfc-summary output.** Extend the `/rfc-summary` skill to also surface entries from `docs/rfc-braindump.md` alongside the existing Draft and Approved RFC groupings, so the standup-style snapshot covers the full RFC workflow rather than just promoted proposals. This prevents parked ideas from becoming invisible and losing track of unpromoted candidates. Key constraints: keep the output read-only and inline (no agent spawn), preserve the existing grouping format, and decide on a clear visual separation (e.g. a "Braindumps" section after Draft/Approved) plus whether to show all entries or cap at a reasonable count given the parking lot can grow large.
* **Audit skills for deterministic-script consolidation; settle Python dependency policy.** Sweep every skill under `skills/` and `.claude/skills/` and push each step that does not require LLM reasoning into a condensed bash script, leaving the LLM only the genuinely reasoning-shaped work — the same consolidation pattern recently applied to `/sync`. The trigger is that `sync-summary.py` slipped in as an implicit hard Python dependency without a policy decision, and macOS has not shipped Python by default since 12.3. The RFC must resolve the standing question: keep Python (then add a `python3` probe to `scripts/check-requirements.sh` and document the install requirement) or ban it in favor of bash+jq across the board (as already done when `sync-summary.py` was rewritten). Constraints: preserve current skill behavior, keep scripts idempotent, and audit must produce a per-skill before/after map so reviewers can validate the LLM-vs-script split per skill.
