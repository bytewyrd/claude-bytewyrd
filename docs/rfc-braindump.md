# RFC Braindump

Potential RFC ideas. Add with `/rfc-braindump`, promote to full RFC with `/rfc-new`.

* **Enforce evidence-based research for rfc-architect.** Update the `rfc-architect` agent's instructions to require verification of all external facts (APIs, library behavior, tool capabilities, version-specific details) via Context7 or Exa before including them in an RFC — training knowledge alone is not an acceptable source. This addresses the risk of RFCs being drafted with outdated or hallucinated technical details that later derail implementation. Approach hints: mirror the "Evidence-Based Development" guidance already in `CLAUDE.md`, and consider adding a self-check step to the RFC self-review checklist that flags unverified claims.
* **`/rfc-summary` command for active RFC overview.** Add a new skill/command that lists all RFCs currently in `Draft` or `Approved` status, filtering out `Done` and `Dropped` entries to surface only work that is pending design feedback or awaiting implementation. This solves the discoverability problem of scanning `docs/rfcs/` manually to figure out what's in-flight, especially as the parking lot grows. Output should be concise (e.g., status, title, identifier) so it works as a quick standup-style snapshot rather than a full report.
* **Post-Approval Discretionary Revisions section in RFC template.** Add a dedicated section to the RFC template where implementers can log small clarifications, typo fixes, or non-breaking adjustments made after an RFC reaches Approved status, without requiring a full re-approval cycle. This solves the current ambiguity around minor in-flight changes during implementation — today there's no clear place to record them, so they either bloat commit messages, get lost, or trigger unnecessary re-review. Constraints: revisions must be non-breaking and not alter the core design decisions; anything substantive should still go back through review. The section should make it easy to audit what changed between Approved and Done states.
* **`/sync` enforces GitHub branch auto-delete setting.** Extend `/sync` to inspect a project's GitHub repository settings (when the project is hosted on GitHub) and ensure that "automatically delete head branches after merge" is enabled, bringing remote configuration under the same idempotent convention-enforcement umbrella that currently only covers local repo state. This solves the recurring problem of stale merged branches accumulating on the remote because the setting was never flipped on at repo creation. Key constraints: detect GitHub remotes reliably, use the GitHub MCP (or `gh` CLI fallback) with appropriate auth scopes, skip cleanly on non-GitHub remotes or when permissions are insufficient, and surface the change to the user rather than silently mutating remote settings.
* **Drop dates from BEST_PRACTICES entries.** Remove date stamps from all entries in `~/.claude/BEST_PRACTICES.md` and `docs/BEST_PRACTICES.md`, and update the `best-practices-record` and `best-practices-extract` skills to stop emitting them. Dates add noise without signal: a practice's value is its content, not when it was first captured, and stale dates make entries feel outdated even when the lesson is still correct. Scope covers stripping dates from existing entries, updating the writer skills, and confirming `best-practices-sync` (which promotes entries into plugin sync content) does not rely on dates for ordering or deduplication.
* **User-scope installation with requirement-check hooks.** Allow the bytewyrd plugin to be installed at user scope (applying globally across all projects) rather than requiring per-project installation. Add session-start or pre-task hooks that verify the active project meets the plugin's runtime requirements — companion plugins installed, required MCP servers configured, expected tooling present — and surface clear warnings or errors when prerequisites are missing. This removes the friction of per-project setup while preserving correctness: instead of enforcing requirements through installation scope, enforce them at the moment they actually matter. Open questions: which checks are warnings vs. hard failures, how to make the diagnostics actionable (e.g., point to the exact fix), and whether some skills should silently no-op on unsupported projects rather than warn.
* **Unify destination of `/best-practices-record` and `/best-practices-extract`.** Today `/best-practices-record` writes manually-captured entries to the global `~/.claude/BEST_PRACTICES.md`, while `/best-practices-extract` writes session-distilled entries to the project-local `docs/BEST_PRACTICES.md` — an inconsistency that splits the same conceptual data across two destinations with no clear rationale. The RFC should pick an intentional model: either both skills target the same file, or each writes to a clearly-justified scope with an explicit promotion path between local and global (e.g. extract-to-local then curate-to-global via `/best-practices-sync`). Key questions to resolve: what belongs project-local vs. cross-project, how does an entry get promoted, and does `/best-practices-extract` need a global-write variant for stack-level lessons surfaced mid-session.
* **Auto-run /best-practices-extract on PreCompact.** Today the PreCompact hook only prints a reminder, leaving extraction as an opt-in user action; the human should be deciding which learnings to keep, not whether to extract at all. Make extraction actually fire before compaction wipes the context. Constraint: hooks are shell commands and a spawned `claude` lacks the live session's history, so direct skill invocation isn't viable. Directions to explore: emit a strongly imperative hook message Claude treats as mandatory rather than advisory; investigate any Claude Code mechanism allowing hooks to trigger in-session skill execution with conversation context; or restructure so extraction is a first-class step of the compaction flow itself rather than a user-triggered side task.
* **Modular Plugin Feature Toggles.** Restructure the plugin so it ships as a set of opt-in features (e.g., RFC workflow, refactor skill, best-practices extraction) that consumers can enable or disable during `/sync` setup, with a small set of core features that are always installed. This solves the current all-or-nothing adoption problem — some projects don't want or need the RFC process, but today installing the plugin means inheriting everything. Key design questions to resolve later: which features qualify as core vs. optional, how the toggle state is stored and re-applied on `/sync` re-runs, and how features declare their boundaries so they can be cleanly excluded without breaking cross-feature references.
* **Auto-prompt PR creation in /rfc-new and parallelize /rfc-new-braindumps.** Extend `/rfc-new` so that whenever GitHub is available (gh CLI authenticated or the GitHub MCP responding), it always asks the user whether to open a PR for the freshly drafted RFC, removing the current manual step of pushing and opening one by hand. Additionally, refactor `/rfc-new-braindumps` to fan out a parallel workflow that invokes `/rfc-new` once per braindump entry concurrently, rather than processing them sequentially, so converting an accumulated batch of ideas into Draft RFCs scales with the number of items instead of with total runtime.
* **Auto-rehydrate context after compaction.** Build a mechanism that, immediately after a compaction event, automatically reloads a curated set of high-value files back into context so the agent doesn't lose critical working memory. Selection must be deliberately conservative — pulling everything defeats the point of compaction — and should prioritize files actively being edited, the current plan/RFC, and project conventions over speculative dependencies. Open questions: how to detect "important" (recency, edit count, explicit pinning, plan references?), where the policy lives (settings, hook, skill), and how to avoid re-bloating context with stale or tangential files.
* **Tight worktrunk integration for worktree workflows.** Replace the plugin's manual `git worktree add` conventions with first-class integration of the `worktrunk` CLI, so session-start checks, new-branch creation, and worktree cleanup all flow through worktrunk's commands and hooks rather than ad-hoc git plumbing. This consolidates worktree management into a single well-tested tool, lets the plugin lean on worktrunk's project hooks (`.config/wt.toml`) for commit-message generation and automation, and removes drift between the plugin's documented workflow and what users actually run. Key constraints: worktrunk must be available on the user's PATH (graceful fallback or clear setup guidance when missing), and existing skills (`/sync`, RFC implement, branch cleanup) need to be updated to invoke worktrunk consistently instead of raw git commands.
* **Enforce branch+PR discipline in /rfc-new.** Update the `/rfc-new` skill so that creating any RFC — including promoting braindump entries — always creates a dedicated `rfc/<slug>` branch and opens a PR, never committing directly to main. This addresses a real failure where three Draft RFCs (#7, #13, #25) landed on main via bulk commit 346fe6a, bypassing review entirely. Branch creation and PR opening must be non-optional steps in the skill flow, and bulk braindump promotion should parallelize the branch+PR workflow per-RFC rather than batching multiple RFCs into a single commit.
* **Scope best-practices extraction to non-inferable guidance.** Tighten the triage criteria in `best-practices-extract` so it captures only lessons an agent cannot reasonably rediscover on its own — decisions made by project maintainers, community conventions accreted over time, taste-driven defaults, and other context that lives outside the code. Things an agent can recover by running the failing command (CLI error messages, missing flags, obvious tool misuses) should be excluded, since reproducing the symptom is already the recovery path. The goal is to keep the best-practices pool dense with durable human judgment rather than diluting it with self-discoverable facts.
* **Standardize on merge commits for PR integration.** Update agent instructions and project conventions to require merge commits (rather than rebase or squash) when merging PRs and when pulling `main` into a feature branch. Rebase remains acceptable in narrow cases, but the default avoids rewriting history on shared branches — protecting existing checkouts from forced updates and preserving an auditable record of conflict resolution at the merge point. Capture this guidance where agents and humans will both see it (likely `CLAUDE.md`, commit/PR skills, and any relevant agent definitions) so behavior is consistent across `/commit-push-pr`, RFC implementation, and ad-hoc merges.
* **Extend `/github-verify` to enforce merge-commit-only repo settings.** Add a check to the `/github-verify` skill that inspects each repository's GitHub merge strategy settings and flags any repo that allows squash or rebase merges — only merge commits should be permitted. This complements the existing agent-level instruction to standardize on merge commits by enforcing the policy at the GitHub layer, where it can't be bypassed by a contributor choosing the wrong button. Pairs with the prior braindump on merge-commit standardization; together they form a belt-and-suspenders setup (agent guidance + repo configuration).
